# 更换配置时自动备份与迁移历史

本文说明当前源码的历史处理流程。[下载客户端](https://github.com/yunhui201/yunhui.me/releases/latest) · [安装说明](../INSTALLATION.md) · [客户端配置指南](CLIENT-CONFIGURATION.md)

ChatGPT / Codex 的编程历史可能按客户端配置中的供应商标识分开显示。云汇将这些分组称为“供应商区域”，例如 `openai`、`yunhui` 或你自己设置的标识。区域名称不是模型名称，也不是云汇供应商列表中的编号。

为兼容的 **ChatGPT / Codex 桌面客户端或 Codex CLI** 应用、重新应用配置，以及恢复原配置时，云汇先保存配置，再尝试备份和衔接历史归属。历史暂时无法处理不影响配置保存。

## 应用新配置

1. 在 **客户端接入** 选择客户端、供应商和模型，点击 **预览配置**。
2. 核对供应商、模型和实际配置目录，按需展开历史说明。
3. 点击 **保存配置**，云汇先备份原配置，再保存新配置。客户端仍在运行也可以完成这一步。
4. 看到配置保存成功后，保存手头工作，再重新启动客户端加载新配置。
5. 历史处理结果可展开查看；已经完成备份的批次会显示实际数量与位置，暂未处理的历史可稍后在历史页面单独整理。

自动历史处理范围是本次配置目录内的**全部未归档、已归档和子任务会话**。客户端已退出且历史可处理时，云汇会完整备份会话文件及发现的历史索引数据库，包括无需修改的会话，再同步供应商归属与可确认的路径。配置在此之前已经保存；历史处理成功与否不会撤销配置。

只有索引、找不到本机会话原文件的记录，会随索引数据库完整备份并原样保留，不阻止配置应用；这类记录会单独显示数量，不计入已修复或会话文件备份数量。云汇不会删除这些索引，也不会猜测补建聊天内容。后续找回原文件后，可重新预览处理。

历史内容损坏、编码异常、索引重复、原文件缺少必要索引或路径无法确认时，云汇在能够完成历史备份的情况下跳过这些会话的修复。原文件留在原处，备份另存一份；不会移动或删除历史来强行修复。跳过原因随备份保存，可在结果中查看。

索引结构无法识别、无法确认关联范围时，本次历史只备份、不改写，客户端配置仍可继续保存。修复不了的旧会话不必先处理完，也不会因此禁用应用按钮；是否能在原客户端继续读取，取决于原文件本身是否完整。

客户端正在运行、历史库被占用、历史无法读取或无法备份时，本次历史处理会暂缓或显示未完成，配置继续保存。界面会明确区分“配置已保存”和“历史未处理”，不会把未完成的历史备份报告为成功。保存配置不会自动终止正在执行的 CLI 或桌面任务。

## 旧会话提示供应商已移除

旧会话可能仍引用以前的供应商标识。重新保存配置时，云汇会从可读取的本机配置、历史索引和会话头识别这些标识，为缺失项补充兼容连接，再按条件独立整理历史。客户端运行中或部分历史损坏，都不会因此阻止新配置保存。

本地网关的兼容连接绑定此次选择的供应商与模型，不按旧模型名称随意选择其他服务；官方账号共存保持官方认证与第三方密钥分开处理。直连使用所选供应商的地址与密钥，旧模型不受支持时可在原客户端改选模型。现有独立供应商配置、官方登录和聊天正文保留。

自动整理成功的旧会话会进入专用兼容区域，避免客户端恢复时沿用旧模型名称而请求失败。新会话的默认模型与正常模型菜单不受此区域影响。使用 Codex CLI 续聊时，从云汇历史页面复制 **恢复命令**，命令会带上该会话实际的供应商区域。

遇到这个提示，升级云汇后重新选择供应商与模型，点击 **保存配置**，保存工作并重启原客户端，再打开原会话。历史文件完全无法读取时，无法保证识别其中所有旧标识；这不会挡住新配置和新会话的使用。

## 恢复原配置

在客户端卡片选择 **恢复 → 恢复原配置**，先恢复配置，再独立尝试将当前会话衔接到原配置使用的供应商区域。历史暂未处理不影响恢复配置，完成后重新启动客户端即可。

这会保留当前会话正文和之后新建的会话，不会把历史整体倒退到首次接入时的内容。只想撤销高级执行权限时，使用 **恢复原执行权限**；该操作保留供应商连接。

## 备份、失败与中断

历史处理完成时，结果会显示实际备份的会话文件数和索引数据库数，以及已修复、无需修改、原样保留、备份后跳过的记录数和历史备份位置。暂未处理时只说明原因，不承诺已经备份或修复。只有索引的记录在数据库备份中，不会显示为已备份的会话文件。备份保存在本机；配置备份可能包含 API Key，应与原配置一样妥善保管。

历史迁移失败时，会尝试撤销本批次的历史修改并保留备份，已保存的客户端配置继续有效。配置自身保存失败时，才会尝试撤销本次配置修改。若发现外部改动，保留当前内容并说明原因；不要为了重试而删除原历史或备份。

程序意外退出后，未完成的配置保存与历史修复分别处理。旧历史批次不会自动把后来保存的新配置改回去；未完成的历史可在独立历史工具中查看和处理。

需要单独撤销某次历史迁移时，进入 **历史会话 → 批量修复历史 / 区域迁移 → 修复备份与恢复**，选择批次并 **预览恢复**。这个入口恢复历史修改；切回客户端原配置应使用客户端卡片上的 **恢复原配置**。

## 哪些内容会保留

迁移修改的是会话供应商归属和能确认的路径，不会更改会话 ID、聊天正文、归档状态、父子任务关系或原客户端登录文件，也不会把会话文件搬到另一个目录。

处理范围限于当前选择的 Codex 配置与历史目录。其他 `CODEX_HOME` 目录、远程电脑、Claude 历史和云端聊天不会被一起迁移；请先在预览中核对实际路径。

加密字段会保持原样。**迁移归属不会转换原账号或原供应商的加密身份，也不保证旧会话能跨账号、跨服务继续使用全部上下文。** 能否续聊取决于原客户端和模型服务；遇到身份不兼容时，可保留旧会话供阅读，并在新服务下新建会话。

## 独立整理指定区域或会话

配置保存后暂未处理的历史，或特定区域和会话，可使用独立入口整理：

1. 进入 **历史会话 → 批量修复历史 / 区域迁移 → 供应商区域迁移**。
2. 选择来源和目标区域，按需限定未归档、已归档或全部历史。
3. 点击 **扫描并预览**，查看每条会话的修改原因，勾选可处理的会话。
4. 退出相关客户端并确认，再点击 **备份并迁移所选**。
5. 重新打开使用目标区域的客户端查看结果。

目标区域以当前实际配置为准；旧区域即使不再用于连接，也可能继续出现在来源列表。独立手动迁移按页面可处理的范围执行，遇到缺失、重复、路径歧义或不支持的子任务记录时会说明原因。手动修复的退出要求与检查不会阻止客户端配置保存。
